For distribution, put config.json next to stl-analyzer.exe and stl-generator.exe. The stl_folder setting controls the default model folder. During cargo run, the project-root config is a development fallback.

End-to-End Data Flow

STL bytes from disk
  -> stl::detect_format
  -> stl::parse_ascii or stl::parse_binary
  -> Vec<Triangle> (three coordinates per face)
  -> Mesh::from_triangles (welds exact duplicate vertices)
  -> indexed Mesh { vertices, triangles: indices }
  -> analysis::analyze
  -> console report or benchmark timings

Useful Rust Concepts in This Project

  • struct groups related data: for example, Triangle contains a normal and exactly three Vec3 vertices.
  • enum expresses alternatives: StlFormat::Ascii or StlFormat::Binary; StlError::Io or StlError::Invalid.
  • Result<T, E> represents successful work or a recoverable error. Parser callers use ? to return an error without a panic.
  • &[T] borrows a slice without copying it. Writers receive &[Triangle].
  • Vec<T> owns a growable list. The parser owns its triangles; welding consumes that vector and builds the indexed mesh.

Parsing STL Files

Binary STL

A valid binary STL is exactly: 80-byte header, 4-byte little-endian triangle count, then 50 bytes per triangle. The parser first checks whether 84 + 50 * count == file length. That structural check is important because a binary header is allowed to start with the text solid.

Each triangle contains 12 floats: three normal components, then three vertices with three components each; the final 2 bytes are an unused attribute count. Non-finite coordinates such as NaN or infinity are rejected.

ASCII STL

The parser requires a UTF-8 document beginning with solid, followed by repeated complete facets:

facet normal nx ny nz
  outer loop
    vertex x y z
    vertex x y z
    vertex x y z
  endloop
endfacet
endsolid name

Being strict produces helpful errors for malformed files. If your mentor wants to accept exporters that omit normals, vary whitespace unusually, or add extra comments, adjust parse_ascii in src/stl.rs and add a regression test first.

Why the Parser Returns Raw Triangles First

STL repeats every vertex for every triangle. A raw triangle list matches the file directly, so parsing is simple. The next stage can then choose the mesh identity policy (currently exact welding) without making format code responsible for mesh topology.

Welding and Indexed Meshes

Mesh::from_triangles walks every raw vertex once. A HashMap<VertexKey, usize> maps an exact coordinate key to the index of the first matching vertex in mesh.vertices. Each output face stores only three usize indices in IndexedTriangle.

Raw faces:       [A, B, C] [B, D, C]
Unique vertices: [A, B, C, D]
Indexed faces:   [0, 1, 2] [1, 3, 2]

Important: this is exact welding. The key uses f32::to_bits(), except -0.0 is normalized to 0.0. Coordinates that differ by even a tiny amount remain separate. That avoids accidentally modifying model geometry, but can leave seams in imperfect exports.

Analysis Rules

Bounding Box

BoundingBox::from_vertices visits each unique vertex and tracks component-wise minimum and maximum X, Y, Z. It returns None for an empty mesh. The squared diagonal is used as a scale-aware area reference.

Sliver Triangles

For each indexed face, the code calculates area from the cross product and finds the longest edge. The aspect ratio is:

aspect_ratio = longest_edge^2 / (2 * area)

A degenerate triangle has zero area and therefore receives infinite aspect ratio. The default warning threshold is 20.0; a larger ratio means a thinner triangle.

Very Large Triangles

The relative-area heuristic is:

relative_area = triangle_area / bounding_box_diagonal_squared

At the default 0.25, a triangle occupying at least one quarter of that reference area is reported. This is scale invariant, but it is not a standard STL rule: a flat or very elongated model may make the result surprising.

High-Incidence Vertices

Each face contributes its three undirected indexed edges. Self-edges from degenerate faces are ignored. Edges are sorted and deduplicated, then each endpoint degree is counted. A vertex is reported when its unique incident-edge count is greater than the configured default of 12.

Sorting a compact Vec<(usize, usize)> is intentional. It avoids a separate hash set for every vertex while still preventing the two faces on a manifold shared edge from being counted twice.

Configuration

{
  "stl_folder": "stl_files",
  "sliver_aspect_ratio": 20.0,
  "large_triangle_area_ratio": 0.25,
  "max_incident_edges": 12
}

All three threshold values must be positive. Keep them in version control with an explanation from the team, because they define what the report calls a warning.

Generators

stl-generator is independent from the analyzer menu. It defaults to binary output, density 24, and the configured STL folder.

Run cargo run --release --bin stl-generator with no arguments for an interactive flow: choose Cube, Cylinder, or Torus, then press Enter to accept each dimension default.

ShapeDimension flagsDefaults
Prism--width --height --depth2 x 1 x 1
Cube--size1
Cylinder--radius --height1, 2
Cone--radius --height1, 2
Sphere--radius1
Torus--major-radius --minor-radius1, 0.35

All dimensions must be finite and positive. For a torus, major radius must be greater than minor radius to avoid a self-intersecting default surface. Density is a mesh-resolution setting, not a physical dimension.

Questions for Your Mentor

These rules are domain decisions, not facts built into STL. Ask and record the answers before changing the defaults.

  1. What exact sliver definition should the project use: aspect ratio, minimum angle, radius ratio, or a manufacturing-specific tolerance?
  2. Should zero-area triangles be reported separately as “degenerate” instead of being included as slivers?
  3. What should “very large” mean for flat, long, or thin models: area versus bounding-box diagonal squared, model surface area, maximum edge length, or an absolute unit?
  4. What are the real model units: millimeters, inches, or unitless coordinates? Are absolute quality thresholds needed in addition to relative ones?
  5. Should nearly equal vertices be welded with a tolerance? If yes, what tolerance is safe and should it be absolute, relative, or both?
  6. Does a high-incidence vertex mean non-manifold topology, a valid CAD feature, or simply a review warning? What threshold applies to your models?
  7. Should the application validate stored STL normals against recomputed geometric normals and warn about inverted winding?
  8. Should malformed ASCII variants be accepted for compatibility, or should strict parsing remain a deliberate quality gate?
  9. Do benchmark requirements include peak process memory, not only final indexed-mesh storage? If yes, choose an OS-specific measurement approach and a reference machine.
